# Serial Debug Output Reference

## Overview
This document describes all serial print debug messages generated by the Temperature Nodes system during boot, pairing, and normal operation. Use this as a troubleshooting reference when testing.

---

## 🔴 NODE STARTUP & PAIRING SEQUENCE

### Boot Start
```
[Node 1] Starting
```
- **When**: Immediately after device powers up
- **What it means**: Firmware has initialized and determined this is a node (ROLE_PIN = HIGH)
- **Next step**: Checks pairing storage

### Pairing Storage Check
```
[Node] Pairing storage unavailable
```
- **When**: If NVS flash read fails during initialization
- **What it means**: Cannot read pairing preferences from storage
- **Action**: Node enters deep sleep; likely hardware issue
- **Recovery**: Reflash firmware

### Battery & Sensor Reading
```
[Node] Reading battery and SHT40
```
- **When**: After storage check passes
- **What it means**: About to sample SHT40 sensor and battery voltage
- **Next step**: Sensor values follow

### SHT40 Sensor Output
```
[Node 1] SHT40: 72.50 F, 45.23 %RH
```
- **When**: Immediately after battery/sensor read
- **What it means**: Successfully read temperature and humidity from SHT40
  - Temperature: in °F (target range 60-85°F for home environment)
  - Humidity: in % (target range 30-60%)
- **Example interpretation**: 72.5°F and 45% humidity is healthy

### SHT40 Initialization Failure
```
[Node] SHT40 initialization failed; sending invalid sensor readings
```
- **When**: If I2C communication with SHT40 fails at startup
- **What it means**: Sensor not responding; likely:
  - Loose wiring on I2C bus (SDA/SCL)
  - Bad solder joint on sensor
  - Device power issue
- **Action**: Still proceeds with pairing but sends -999 as sensor values
- **Recovery**: 
  1. Check I2C wiring (SDA=GPIO5, SCL=GPIO6 on XIAO ESP32S3)
  2. Try reseating sensor
  3. Reflash firmware

### ⭐ FIRST-TIME PAIRING PATH (No prior hub stored)

#### Hub Storage Empty
```
[Node] Using saved hub on channel 6
```
**OR** (if no hub stored):
```
[Node] Searching for a hub (up to 30 seconds)
```
- **When**: Node checks storage for previously-paired hub
- **What it means**: 
  - "saved hub" = Node has prior pairing; using it immediately
  - "Searching" = First time pairing or pairing was cleared

#### Wi-Fi Station Setup
```
[Node] Failed to start Wi-Fi station
```
- **When**: If WiFi.mode(WIFI_STA) fails
- **What it means**: Cannot initialize Wi-Fi radio
- **Action**: Enters deep sleep; hardware issue
- **Recovery**: Reflash firmware

#### ESP-NOW Initialization
```
[Node] ESP-NOW initialization failed: ESP_ERR_WIFI_NOT_INIT
```
- **When**: If ESP-NOW stack fails to initialize
- **What it means**: Radio not ready after Wi-Fi startup
- **Action**: Enters deep sleep
- **Recovery**: Reflash firmware

#### Hub Discovery Starting
```
[Node] Searching for a hub (up to 30 seconds)
```
- **When**: Node begins channel scanning for hub broadcasts
- **What it means**: Will try all Wi-Fi channels (1-14) looking for PAIR_RESPONSE
- **Duration**: Up to 30 seconds if no hub found
- **During scanning**: May see occasional:
  ```
  [Node] Discovery send failed: ...
  ```
  (This is normal during rapid channel switching)

#### ⭐ Hub Found Successfully
```
[Node] Paired with hub on channel 6
```
- **When**: Node receives PAIR_RESPONSE from hub on a specific channel
- **What it means**: 
  - Hub found on this channel ✅
  - Pairing successful
  - Hub MAC address saved to storage
  - Next: will attempt to send first measurement
- **Important**: Channel must match hub's current Wi-Fi channel

#### Pairing Save Failure
```
[Node] Failed to save hub pairing
```
- **When**: After finding hub, cannot write to NVS storage
- **What it means**: Flash storage corrupted or full
- **Action**: Enters deep sleep
- **Recovery**: May need firmware flash with erase

### 🔄 SENDING MEASUREMENT TO HUB

#### Send Attempt
```
[Node] ESP-NOW send failed: ESP_ERR_ESPNOW_NO_PEER
```
- **When**: Node tries to send SensorPacket but hub MAC not added as peer
- **What it means**: Shouldn't happen; indicates pairing save/restore issue
- **Recovery**: Clear node storage and re-pair

#### Measurement Sent
```
[Node] Measurement acknowledged at radio level
```
- **When**: SensorPacket delivered successfully to hub (ESP-NOW callback fired)
- **What it means**: 
  - Radio packet reached hub ✅
  - Hub ESP-NOW ACK received
  - Does NOT mean hub processed it; just radio delivery
- **Next step**: Check for RESET_REQUEST from hub (see "Reset Pairing" below)

#### Delivery Failed
```
[Node] ESP-NOW delivery failed
```
- **When**: After 3 retries (MAX_SEND_RETRIES=2), packet never delivered
- **What it means**: 
  - Hub is not responding on its channel
  - Possible causes:
    - Hub is offline or powered down
    - Hub switched Wi-Fi channels (unlikely while pairing window open)
    - Radio interference
    - Incorrect stored hub MAC address
- **Action**: Still proceeds; will attempt reset response wait, then sleeps

#### Reset Response Wait
If hub has a RESET_PAIRING request queued, node waits up to 1 second for it:

```
[Node] Pairing cleared; searching for a hub
```
- **When**: Node received RESET_PAIRING from hub and successfully cleared storage
- **What it means**: 
  - Hub sent pairing reset command
  - Node has deleted stored hub info
  - Node will re-search for hub on next boot ✅
- **Action**: Proceeds to button reset check, then deep sleep

```
[Node] Failed to clear stored pairing
```
- **When**: Node received RESET_PAIRING but storage write failed
- **What it means**: Flash corrupted or full; can't clear pairing
- **Action**: Enters deep sleep; pairing still in storage (stale)
- **Recovery**: May need erase and reflash

### 🔘 BUTTON RESET (D0 Pairing Reset)

If node is **already paired** and **D0 button is held**, this sequence appears:

```
[Node] Hold D0 for 10 seconds, then release to clear pairing
```
- **When**: User presses D0 button while node is booting
- **What it means**: Button held down; waiting for hold time to complete
- **Action required**: User must hold continuously for 10 seconds

#### At 5 seconds (BUTTON_HOLD_TIME_CONFIG_RESET):
```
[Node] Release D0 to clear pairing
```
- **When**: Button has been held for 5 seconds
- **What it means**: User can now release to trigger pairing clear ✅
- **If released now**: Pairing cleared and node re-searches for hub
- **If held past 10 seconds**: Reset is canceled

#### If held too long (past 10 seconds):
```
[Node] Pairing reset canceled
```
- **When**: User held button for 10+ seconds and then released
- **What it means**: Button held too long; reset NOT executed
- **Action**: Node keeps current pairing; proceeds to send measurement

#### Successful reset via button:
```
[Node] Pairing cleared; searching for a hub
```
- **When**: User released button between 5-10 seconds
- **What it means**: 
  - Stored hub info deleted ✅
  - Node will re-search on next boot
  - Current boot: proceeds to send measurement with old hub, then sleeps

---

### 🔴 DEEP SLEEP ENTRY

```
[Node] Sleeping for 30 minutes
```
- **When**: Node completes its lifecycle (measurement sent or errors encountered)
- **What it means**: 
  - About to enter deep sleep ✅
  - Will wake in 30 minutes via timer
  - Serial output stops here (CPU powered down except RTC)
  - No serial output during sleep
- **Expected behavior**: Device consumes ~100 µA while sleeping

## 🟢 HUB STARTUP & PROVISIONING

### Hub Boot Start
```
[Hub] Starting
```
- **When**: Immediately after power-up (ROLE_PIN = LOW)
- **What it means**: Device is configured as Hub; core initialization beginning
- **Next step**: Sensor initialization

### Time Zone Configuration
```
[Hub] Starting Blynk Edgent
```
- **When**: After timezone is set (PST8PDT)
- **What it means**: About to initialize BlynkEdgent provisioning system
- **What happens before**: SHT40 init, storage checks (may not print)

### SHT40 Sensor Checks
```
[Hub] SHT40 initialization failed; no local readings will be published
```
- **When**: If hub's local SHT40 sensor fails to initialize
- **What it means**: Hub won't have local temperature/humidity
- **Action**: Still runs; nodes can still report to hub
- **Recovery**: Check I2C wiring on hub's sensor

### Storage Issues
```
[Hub] Invalid stored pairing reset state
```
- **When**: Stored reset state from prior hub session is corrupted
- **What it means**: Previous pairing reset data is invalid
- **Action**: Resets to clean state; continues normally

```
[Hub] Pairing reset storage unavailable
```
- **When**: Cannot open NVS storage for reset state
- **What it means**: Flash storage unavailable
- **Action**: Still runs but cannot perform reset operations
- **Recovery**: Reflash firmware

### Blynk Edgent Initialization
```
[Hub] Blynk Edgent initialization failed
```
- **When**: BlynkEdgent.begin() returns false
- **What it means**: Cannot initialize provisioning; likely network/crypto issue
- **Action**: Hub enters error loop; no Wi-Fi or pairing possible
- **Recovery**: Check provisioning configuration; may need firmware reflash

## 🔄 HUB PROVISIONING STATE TRANSITIONS

As user provisions hub via BLE, you'll see these in order:

### 1. Waiting for Provisioning
```
[Hub] Waiting for Blynk provisioning
```
- **When**: Hub starts and BlynkEdgent is ready
- **What it means**: Waiting for user to enter Wi-Fi credentials via phone app
- **Action**: User opens Blynk app and scans BLE provisioning QR code

### 2. Wi-Fi Connecting
```
[Hub] Wi-Fi connecting
```
- **When**: User entered Wi-Fi SSID/password in app
- **What it means**: Hub is attempting to connect to Wi-Fi
- **What happens before**: May see verbose Blynk logs (optional BLYNK_LOG output)

#### If Wi-Fi fails:
```
[Hub] Wi-Fi disconnected or connection failed (reason 201)
```
- **When**: Wi-Fi connection attempt fails
- **What it means**: Check reason code (common: 201=password incorrect, 15=SSID not found)
- **Action**: Returns to provisioning state; waits for new credentials

#### If Wi-Fi connects:
```
[Hub] Wi-Fi connected to access point; waiting for IP address
[Hub] Station MAC: AA:BB:CC:DD:EE:FF, Wi-Fi channel: 6
```
- **When**: Successfully joined Wi-Fi network
- **What it means**: 
  - Connected to AP ✅
  - Hub MAC shown (save this if needed for network debugging)
  - Wi-Fi channel shown (nodes will search this channel)
  - Waiting for DHCP IP address

### 3. IP Address Acquired
```
[Hub] Wi-Fi connected and IP address acquired
```
- **When**: DHCP lease obtained
- **What it means**: Hub now has IP address; can reach Blynk servers
- **What happens next**: Attempts connection to Blynk cloud

### 4. Connecting to Blynk Cloud
```
[Hub] Connecting to Blynk
```
- **When**: After Wi-Fi connected and IP obtained
- **What it means**: About to establish TLS connection to Blynk servers
- **What happens before**: May see verbose SSL handshake logs

#### If Blynk connection fails:
```
[Hub] Blynk Edgent connection error; see preceding logs
```
- **When**: Cannot reach or authenticate with Blynk cloud
- **What it means**: Check preceding logs for SSL errors, auth tokens, etc.
- **Common cause**: AUTH token mismatch or not in Blynk app template
- **Action**: Returns to provisioning loop

### 5. Ready for Operation
```
[Hub] Blynk connected; open a pairing window with V41 or the D0 button
```
- **When**: Successfully connected to Blynk cloud ✅
- **What it means**: Hub is provisioned and online
  - Ready to receive nodes via pairing window
  - All 25+ datastreams ready to publish
  - V41 (pairing) control active
  - D0 button active for manual pairing open
- **Next step**: User taps V41 in app or presses D0 to open pairing window

## 🟡 HUB NORMAL OPERATION

### Opening Pairing Window

#### Via App V41:
```
[Blynk] Requesting V100 sync
```
- **When**: Hub connects to Blynk (normal behavior)
- **What it means**: Hub is syncing V100 (demo mode flag) with app

#### User taps V41 button:
```
[Hub] Waiting for node pairing (window open for 2 minutes)
```
- **When**: V41 button pressed in Blynk app
- **What it means**: 
  - Pairing window is OPEN ✅
  - Nodes can now pair for 2 minutes (120 seconds)
  - Hub is listening for PAIR_REQUEST from nodes
- **What happens next**: Nodes discovery messages received

#### Pairing Window Expires:
```
[Hub] Pairing window closed
```
- **When**: 2 minutes elapse after pairing opened
- **What it means**: Window is CLOSED; nodes can no longer pair
- **Action**: Nodes that sent PAIR_REQUEST will not receive PAIR_RESPONSE

#### Pairing Requires Active Connection:
```
[Hub] Pairing requires an active Wi-Fi and Blynk connection
```
- **When**: User tries to open pairing window but Wi-Fi or Blynk is down
- **What it means**: Cannot pair nodes without cloud connection
- **Action**: Wait for Wi-Fi/Blynk to reconnect, then try pairing again

---

### Receiving & Publishing Data

#### Receiving Node Measurement:
```
[Hub] Node 1 report: 72.50 F, 45.23 %RH
```
- **When**: Hub receives SensorPacket from node via ESP-NOW
- **What it means**: 
  - Node 1 sent data successfully ✅
  - Temperature: 72.50°F
  - Humidity: 45.23%
  - Next: Hub publishes to Blynk using beginGroup/endGroup batching

#### Local Sensor Reading:
```
[Hub] Local SHT40: 72.50 F, 45.23 %RH
```
- **When**: Hub's local sensor samples (every 30 minutes)
- **What it means**: Hub's own temperature/humidity
- **What happens next**: Published to Blynk along with node data

#### Publishing to Blynk (Batch):
(No explicit serial message for each virtualWrite)
- The 25+ virtualWrite calls are wrapped in `beginGroup()` / `endGroup()`
- Results in one batch message on Blynk cloud with shared timestamp
- Orbs see consistent, synchronized data when fetching via External API

#### Offline Node Detection:
```
[Hub] Node 2 offline after 3 missed reports
```
- **When**: Node hasn't reported for 90 minutes (3 × 30-min sleep cycle)
- **What it means**: Node considered OFFLINE
  - Last contact: show timestamp "15:30" or "OFFLINE 15:30"
  - Likely causes:
    - Node powered off
    - Node pairing cleared
    - Persistent radio interference
    - Node stuck in restart loop
- **Action**: Blynk app shows "OFFLINE" status for that node
- **Recovery**: Check node battery, re-pair if needed

## 🔴 PAIRING RESET FROM HUB

If user sends pairing reset via V40:

```
[Hub] Pairing reset queued for all nodes
```
- **When**: User taps V40 button in Blynk app
- **What it means**: 
  - Hub will send RESET_PAIRING packets to ALL nodes
  - Next time each node reports, it will receive reset message
  - After reset: node clears stored hub MAC and re-searches
- **Nodes affected**: All currently-paired nodes
- **Recovery time**: Up to 30 minutes (until next node wakes from sleep)

#### Reset Succeeded:
```
[Hub] Pairing cleared for node 1
```
- **When**: Hub receives RESET_ACK from node confirming reset
- **What it means**: Node 1 has successfully cleared pairing ✅
- **Next step**: Node will re-search for hub on next boot

#### Reset Failed:
```
[Hub] Pairing response for node 1 failed: ESP_ERR_ESPNOW_NO_PEER
```
- **When**: Hub tries to send PAIR_RESPONSE but node not in peer list
- **What it means**: Shouldn't happen during normal operation
- **Action**: Can try pairing again after window expires and re-opens

## 📊 NORMAL HUB LOOP CYCLE (repeats every 1-5 seconds)

```
[Hub] Node 1 report: 72.50 F, 45.23 %RH
[Hub] Node 2 report: 68.30 F, 52.10 %RH
[Hub] Local SHT40: 72.50 F, 45.23 %RH
[Blynk] ◀ virtualWrite(V0, 72.50)
[Blynk] ◀ virtualWrite(V1, 68.30)
[Blynk] ◀ virtualWrite(V4, 45.23)
...
[Blynk] ◀ endGroup()
```
- **Pattern**: 
  1. Node reports (if new data)
  2. Local sensor samples (every 30 min)
  3. Begin batch group
  4. Multiple virtualWrite calls
  5. End batch group
  6. Batch sent to Blynk as one transaction with shared timestamp

## 🧪 TESTING SERIAL OUTPUT INTERPRETATION

### Successful Full Cycle (Node)
Expected order when node boots and pairs:
```
[Node 2] Starting                                          ← Boot
[Node] Reading battery and SHT40                           ← Sensor init
[Node 2] SHT40: 73.10 F, 48.50 %RH                        ← Reading OK
[Node] Searching for a hub (up to 30 seconds)             ← First pairing
[Node] Paired with hub on channel 11                       ← Found hub ✅
[Node] Measurement acknowledged at radio level             ← Sent OK
[Node] Sleeping for 30 minutes                             ← Sleep
```
**Interpretation**: Node paired successfully and sent measurement ✅

### Successful Full Cycle (Hub)
Expected order when hub boots and waits for nodes:
```
[Hub] Starting                                             ← Boot
[Hub] Waiting for Blynk provisioning                       ← BLE ready
[Hub] Wi-Fi connecting                                     ← User enters SSID/pwd
[Hub] Wi-Fi connected to access point...                   ← Connected
[Hub] Connecting to Blynk                                  ← Auth
[Hub] Blynk connected; open pairing window...              ← Ready ✅
[Hub] Waiting for node pairing (window open...)            ← User opens window
[Hub] Node 1 report: 72.50 F, 45.23 %RH                   ← Node appears
```
**Interpretation**: Hub provisioned and ready to receive nodes ✅

## 🐛 TROUBLESHOOTING GUIDE

| Serial Output | Problem | Solution |
|---|---|---|
| `[Node] ESP-NOW initialization failed` | Radio won't start | Reflash firmware |
| `[Node] SHT40 initialization failed` | Sensor not responding | Check I2C wiring (GPIO5/6) |
| `[Node] Failed to save hub pairing` | Storage corrupted | Erase flash; reflash |
| `[Node] Searching for hub` after pairing | Hub offline or wrong channel | Power-cycle hub; check Wi-Fi channel |
| `[Node] ESP-NOW delivery failed` after 3 retries | Hub not responding | Hub offline; check radio link |
| `[Hub] Blynk Edgent initialization failed` | Provisioning won't start | Reflash with correct template |
| `[Hub] Pairing requires active Wi-Fi` | Can't open pairing window | Reconnect Wi-Fi first |
| `[Hub] Node X offline after 3 missed reports` | Node not waking | Check node power; battery may be dead |
